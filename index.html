Decisión de arquitectura: snapshot vs. consulta en vivoArchitectural decision: snapshot vs. live query

Cada herramienta disparaba varias consultas SPARQL de agregación contra el catálogo completo en cada carga: costoso para el servidor y lento para el usuario, para calcular cifras que cambian una vez por semana. Analicé herramienta por herramienta y encontré que el espacio de parámetros del usuario era de 3 a 10 combinaciones fijas, no texto libre — o sea, enumerable.

La regla que fijé: los agregados se precalculan, los documentos se consultan en vivo. Cinco de las siete herramientas leen sus KPIs, rankings y distribuciones de snapshots JSON; en el momento en que el usuario hace clic para ver documentos concretos, la consulta va a SPARQL sin excepción. Las otras dos —Perfil de Autor y Buscador de Normas— son búsquedas puntuales, no agregados, y siguen 100 % en vivo: precalcular miles de perfiles de autor no tendría sentido.

Los snapshots se generan con Node leyendo el Turtle del catálogo directamente, sin necesidad de tener el triplestore levantado, en una corrida que parsea el archivo una sola vez para los cinco. El cambio tocó una función por herramienta — el resto de la lógica de graficado no cambió una línea.

Every tool fired several aggregation queries against the full catalogue on each load: expensive for the server and slow for the user, to compute figures that change once a week. I analysed each tool and found the user's parameter space was 3 to 10 fixed combinations, not free text — enumerable, in other words.

The rule I set: aggregates are precomputed, documents are queried live. Five of the seven tools read their KPIs, rankings and distributions from JSON snapshots; the moment a user clicks through to actual records, the query goes to SPARQL without exception. The other two — Author Profile and the Standards-by-Object Finder — are point lookups rather than aggregates, and stay fully live: precomputing thousands of author profiles would make no sense.

The snapshots are generated with Node reading the catalogue's Turtle directly, with no need for the triplestore to be running, in a single run that parses the file once for all five. The change touched one function per tool — the rest of the charting logic did not change a single line.

Auditoría de seguridad del propio códigoSecurity audit of my own code

Audité las siete herramientas de BiblioData y sus puntos de integración. Hallazgos reales y corregidos:

  • XSS reflejado explotable por enlace compartido: el término buscado se insertaba sin escapar en el mensaje de "sin resultados", y ese término viaja dentro de la URL que genera el botón Compartir. Bastaba con mandar un enlace para ejecutar código en el navegador de quien lo abriera.
  • Escapado insuficiente en atributos: escapar con entidades HTML no alcanza para un valor dentro de un onclick, porque el navegador decodifica el atributo antes de pasárselo al parser de JavaScript. Requirió una función de escape aparte para ese contexto.
  • Orden de escapado en literales SPARQL: se escapaba la comilla sin escapar antes la barra invertida, lo que permite cerrar el literal antes de tiempo. Corregido en las doce construcciones afectadas.
  • Inyección de fórmulas en las exportaciones CSV: un valor que empieza con = o @ se ejecuta como fórmula al abrir el archivo en la planilla del usuario.

Dos hallazgos quedaron marcados como no corregidos deliberadamente, con el motivo escrito: eliminar 'unsafe-inline' de la política de contenido exige reescribir todos los manejadores inline del sitio o generar nonces por petición, imposible en un sitio estático; y endurecer el endpoint de consultas requiere acceso al servidor productivo. Distinguir lo que arreglaste de lo que decidiste no arreglar, y por qué, vale tanto como la corrección.

A esto se suman auditorías de SEO y accesibilidad del sitio completo, y la auditoría de integridad que verifica que el grafo publicado se corresponda con las bases de origen.

I audited the seven BiblioData tools and their integration points. Real findings, all fixed:

  • Reflected XSS exploitable via a shared link: the search term was inserted unescaped into the "no results" message, and that term travels inside the URL produced by the Share button. Sending someone a link was enough to run code in their browser.
  • Insufficient escaping in attributes: HTML-entity escaping is not enough for a value inside an onclick, because the browser decodes the attribute before handing it to the JavaScript parser. This needed a separate escape function for that context.
  • Escaping order in SPARQL literals: the quote was escaped without first escaping the backslash, which allows closing the literal early. Fixed across the twelve affected constructions.
  • Formula injection in CSV exports: a value starting with = or @ executes as a formula when the user opens the file in a spreadsheet.

Two findings were marked deliberately not fixed, with the reasoning written down: removing 'unsafe-inline' from the content policy would require rewriting every inline handler on the site or generating per-request nonces, impossible on a static site; and hardening the query endpoint requires production server access. Distinguishing what you fixed from what you chose not to fix, and why, is worth as much as the fix.
